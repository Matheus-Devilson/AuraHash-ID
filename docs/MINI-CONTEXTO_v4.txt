--- VISION DEL PROYECTO ---
AuraHash ID es un protocolo universal de identificacion fisica-digital.
Combina:
- Nucleo: Data Matrix (ISO/IEC 16022) legible por Google Lens, WeChat,
  camaras nativas.
- Seguridad Visual: "Aura Estocastica" (ruido determinista via SHA-256),
  efecto avalancha.
- Criptografia: AES-256-GCM + zlib en capas sensibles + firma digital
  Ed25519 end-to-end.
Filosofia: 100% Offline-First. Privacidad por Diseno. Cero dependencia
de servidores en lectura. Codigo abierto (MIT).

--- ARQUITECTURA DE DATOS (3 CAPAS) ---
- capa_publica: JSON MINIFICADO (claves cortas), visible con Google
  Lens. Cero datos sensibles. Contiene el campo "perfil".
- capa_medica: Datos de salud. zlib + AES-256-GCM al vuelo.
- capa_administrativa: Datos legales/financieros. zlib + AES-256-GCM.

--- 4 PERFILES DE APLICACION ---
Formalizados en docs/PERFILES.md. El campo "perfil" va dentro de
capa_publica y se minifica como "p".

1. salud:        Emergencias medicas. PUB + MED + ADM. RBAC futuro.
2. contacto:     Ninos/mascotas/adultos mayores. PUB solo. Cero cripto.
3. verificacion: Boletos/activos con estado. PUB + ADM. Requiere lista
                 firmada offline para estado dinamico.
4. legal:        Contratos/certificaciones. PUB + ADM. Firma del emisor.

--- FORMATO DEL PAYLOAD (v2.4.1) ---
PUB:{json_minificado}|MED:AES256GCMZ:{base64}|ADM:AES256GCMZ:{base64}|SHA:{32hex}|SIG:{base64}

Prefijos de cifrado:
- "AES256GCMZ:" -> zlib + AES-256-GCM (formato actual v2.3.0+)
- "AES256GCM:"  -> solo AES-256-GCM (formato legacy v2.1.0, reader
                   aun lo acepta)

Mapa de claves cortas PUB (generator.MAPA_CLAVES_PUB):
  perfil->p, tipo->t, instruccion->i, nombre_pila->n,
  alergias_criticas->a, id_visual->v, evento->e

Mapa inverso en reader.MAPA_CLAVES_PUB_INV.

- generator.py v2.4.1 funcional:
  - Data Matrix real (segno).
  - Aura estocastica (numpy + Pillow).
  - SHA-256 maestro de las 3 capas (64 chars internos para Aura).
  - SHA truncado a 32 hex en payload.
  - zlib + AES-256-GCM al vuelo de capas medica/admin.
  - PUB minificado (claves cortas) antes de serializar.
  - Firma Ed25519 del mensaje PUB|MED|ADM|SHA.
  - Muestra perfil de cada escenario durante la generacion.
  - .gitkeep inexistente (fue eliminado por ser JSON basura).

- reader.py v1.4.0 funcional:
  - Pide payload por consola con input().
  - Parsea bloques PUB/MED/ADM/SHA/SIG.
  - Detecta el perfil (salud/contacto/verificacion/legal) en PUB.
  - Descifra MED y ADM con keys/aes.key (soporta zlib y legacy).
  - Desminifica PUB para mostrarlo legible.
  - Verifica integridad SHA-256 (completo o truncado).
  - Verifica firma Ed25519 (informativa, nunca bloqueante).
  - Imprime con formato legible.

- keys_manager.py funcional:
  - Genera par Ed25519 (privada 32 bytes + publica 32 bytes).
  - Aborta si ya existen llaves (a menos que se use --force).
  - Imprime rutas y advertencias.

--- PENDIENTES FUTUROS (features grandes, requieren chat propio) ---
A. RBAC por rol (envelope encryption). Para perfil salud:
   - Datos cifrados una vez con DEK (Data Encryption Key).
   - DEK cifrada por separado para cada rol (paramedico, medico,
     hospital, aseguradora).
   - Cada rol lleva su par X25519 (derivable de Ed25519).
   - Payload crece +N*100 bytes.
   - Idea: dividir DATA en bloques tematicos (critica, clinica,
     financiera) y dar sobres selectivos por bloque.

B. PWA / App Reader para no-programadores:
   - Hoy reader.py es script Python de consola. Inutil para
     un paramedico.
   - PWA instalable desde URL (offline-first con Service Worker).
   - Web Crypto API soporta AES-GCM y Ed25519 en navegadores
     modernos (verificar compatibilidad).
   - Parametro de diseno: cero instalacion, cero Python.

C. Listas firmadas offline (perfil verificacion):
   - Antes del evento, el emisor firma una lista de IDs validos.
   - Las pistolas descargan la lista (firmada con Ed25519).
   - Verificacion offline total sin backend.
   - Refresh T-15min antes del evento (corte de cancelaciones).
   - Ver docs/FLUJO_EVENTOS.md seccion 6.

D. App de staff / pistola digital:
   - Lectura de Data Matrix + verificacion Ed25519 + hash INE.
   - Firmware para pistolas o app movil.
   - Ver docs/FLUJO_EVENTOS.md secciones 8 y 10.

E. Aura Dinamica (boletos digitales):
   - Boleto rotativo cada 30s en el movil del comprador.
   - Imposible fotografiar y revender.
   - Requiere semilla entregada al comprar.

F. Verificacion con estado remoto:
   - Para boletos ya usados y maquinas en mantenimiento.
   - Requiere endpoint del emisor.
   - Rompe offline-first parcial. Cache local mitiga.

G. Campos nuevos en payload del boleto:
   - titular_hash (SHA-256 de INE + nombre).
   - politica_reembolso (modalidad, costo, ventanas).
   - estado (VENDIDO/USADO/CANCELADO/TRANSFERIDO).
   - Ver docs/FLUJO_EVENTOS.md secciones 5 y 7.
